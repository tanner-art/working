# TASK-002 localStorage migration

Owner: Codex B. Implementation ready for orchestrator review; commit pending. This is an incremental React/TypeScript/Vite/localStorage migration. No backend or App.tsx changes are required.

## Stored model and compatibility boundary

The existing `thoughtflow-state-v1` key now stores an envelope with `schemaVersion: 2`, `captures`, `interpretations`, `semanticObjects`, `calendarEvents`, `relationships`, `legacyUiIds`, and unchanged `canvas`. The key name remains stable so existing installations find their data. The new model is written by every successful application save, including new captures; it is not an unused parallel type definition.

`CaptureRecord` owns original expression, source, creation time and context as captured. Semantic objects reference captures and interpretation versions instead of owning authoritative original text. Interpretation versions retain rationale, confidence, review state, proposed work, and historical UI evidence. Existing IDs remain the UI/semantic identity; capture and interpretation IDs are deterministic namespaced derivatives. Migrating does not infer shared capture identity from matching text. Each legacy object becomes a separate capture because earlier provenance cannot establish whether two strings were one expression.

`ThoughtObject`, `ObjectKind` (including its historical `reminder` spelling), and `LegacyInterpretation` are explicitly legacy UI types. `legacyUiProjection` supplies the unchanged `AppState.objects` / `AppState.canvas` contract. `AppState.model` carries the canonical baseline through existing React spreads. `reconcileLegacyUi` records changed readings as additional versions. The store retains the last successful model per loaded snapshot, so subsequent saves from the same React baseline keep all intermediate interpretation versions. Failed saves do not advance that baseline. No canvas element type, geometry, or AppState canvas access changes are required.

The `Interpretation.legacy` snapshot is compatibility/history evidence, not an executable object. It deliberately retains old kind/status/date suggestions, relationships, context edits, and the complete recorded history, but excludes originalContent, source and createdAt, which come from the capture. Unknown object-level fields survive in this evidence; unknown top-level legacy fields cause a load error instead of being silently dropped. Future canonical writers must replace/extend this adapter and validator together: validation currently checks the derivations supported by this incremental adapter, not every possible future many-capture interpretation or independent semantic edit.

## Conservative conversion rules

- Old `confirmed` status or confidence does not establish D-009 confirmation. Legacy Actions and Commitments without newly recorded confirmation remain reviewable interpretations, with their old status retained as evidence. Historical confidence already overwritten by the old app cannot be recovered; migration preserves the value actually stored.
- A legacy Reminder becomes an unresolved reminder proposal in its interpretation. No Action, Commitment, guessed semantic target, scheduled time, or notification is created. When the existing review controls explicitly classify its target, the instruction attaches to that semantic object and remains `needs-review`. Its original wording and old suggested date/deadline remain unresolved evidence. Reminder is excluded from persisted `SemanticKind`.
- The existing dedicated confirmation helper records a timestamped action/obligation gesture and preserves confidence and recorded interpretation. Kind selection or the generic status editor cannot independently create a confirmed Action. This is a minimal adapter for the current control, not TASK-003's complete confirmation UI or transition framework.
- Commitment confirmation does not confirm a fixed deadline or schedule an event. Legacy deadline fields remain in interpretation evidence; the adapter does not promote them to fixed semantic deadlines. CalendarEvents are distinct persisted records with explicit start/time context and optional semantic links. The adapter preserves valid events but does not create them from text. The old fixed-calendar helper returns no items because ThoughtObject cannot represent scheduled events; commitments remain accessible in the object workbench. TASK-007/008 must wire actual event views.
- Existing relationship targets, including dangling historical references and multiple memberships, survive as `legacy-unverified` semantic links with explicit source, target, and interpretation provenance. A proposed identity can be an endpoint before it has accepted semantic meaning. No dependency eligibility or cardinality policy is implemented.
- Voice/canvas records retain their available text and explicitly say `evidence: text-only`. The old app never stored source audio or linked immutable canvas revisions. No provenance is fabricated. Current canvas elements, text, geometry, and connector references are copied intact, including historical dangling connectors.

## Failure and preservation behavior

Load is read-only. Valid legacy state converts in memory; the existing save effect writes the envelope only after successful load. Bad JSON, unknown schema versions, duplicate identities, unsupported top-level content, or invalid canonical references fail loudly through the existing load-error screen. There is no fallback overwrite. Saving also checks that storage still equals the value this session loaded or last wrote, refusing detected changes from another tab. This is an optimistic check, not an atomic cross-tab transaction; localStorage has no compare-and-swap primitive.

Capture source/content/time edits, history truncation, and removal of existing UI identities are refused by this adapter. Archive remains supported for accepted items; unresolved Action/Commitment terminal statuses are preserved as historical evidence but project into Review. Corrections requiring a new capture and destructive deletion need a later explicit workflow. Changed context is interpretation evidence and does not replace capture context. Reclassification appends history while preserving earlier derivations; OD-003 downstream reversal/conflict policy remains undecided, and this adapter does not resolve dependent confirmed edits. OD-007 membership cardinality remains undecided. D-009 already resolves OD-001. Reminder trigger/timezone/delivery policy remains open; no notification delivery is enabled.

Serialization/write failures keep the previous stored value and leave the UI's in-memory work available for retry. Existing JSON download UI is unchanged: its AppState backup includes the original canonical baseline plus current UI state, not necessarily all intermediate canonical versions already saved during that session. For a complete durable canonical export, copy the storage key after a successful save or reload before using the existing download. A canonical backup/import/export surface is follow-up work; no restoration UI is added here. Do not run an older app build against migrated storage: it cannot interpret schema v2. Retain an external copy of the old key if an exact legacy rollback is required.
